# 사용자 기대와 실제 동작의 일치 여부 — UX 평가와 개선안

## 1. 결론

**현재 문제는 ‘버튼이 눌리는가’보다 ‘버튼이 약속한 일이 일어나는가’에 있다.** 하단 ‘▶ 플레이’는 게임을 시작하지 않고, ‘결과 보기’는 다음 게임 안내로 가며, ‘계속하기’는 하던 이야기 문제를 유지하지 않는다. 실제 동작을 재현했다.

색과 장식을 다시 전면 교체하는 것보다 **행동 이름·실제 결과·진행 상태 보존을 맞추는 개선**을 추천한다. 작은 화면에서는 실제 시작 버튼의 발견 가능성도 함께 해결해야 한다.

이번 작업은 운영 앱의 읽기 전용 점검과 개선안 작성이다. **앱 코드 수정·배포는 하지 않았다. 개선안의 사용성 향상은 아직 검증되지 않았다.** 아래 우선도는 영향에 대한 리뷰어 판단이며, 이용률·이탈률을 측정한 결과가 아니다.

## 2. 무엇을 확인했고, 무엇은 아직 모르는가

| 근거 구분 | 이번에 확보한 근거 | 말할 수 없는 것 |
|---|---|---|
| 사용자 관찰 | Sylvie가 하단 플레이를 눌러 시작을 기대했지만 실행되지 않았다고 보고 | 모든 사용자가 같은 실수를 한다는 비율 |
| 운영 동작 재현 | 공개 앱에서 클릭, 취소, 난이도 변경, 키보드 이동, 화면 크기 변경을 실행 | 모든 브라우저·실기기에서 동일하다는 보장 |
| 코드 확인 | 현재 작업 폴더의 이벤트 처리·상태 초기화·문구·시간 설정 확인 | 로컬 HEAD와 운영 배포 SHA가 동일하다는 주장 |
| 전문가 평가 | 문구와 동작의 불일치, 시각적 위계, 손실 방지, 과제 설명 검토 | 독립 참가자의 사용성 검증 또는 임상 타당도 검증 |

검증 환경은 Playwright의 별도 Chromium 세션이다. 기본 글자 크기에서 320×568, 390×844, 768×1024, 1440×900 CSS 픽셀을 확인했다. 브라우저의 첫 화면 위치 측정은 새로 열고 스크롤을 0으로 맞춘 뒤 수행했다. 일부 과제 상태 확인에는 가상 시계를 사용했다. **가상 시계로 얻은 반응 기록은 사람의 수행 능력이나 실제 기기의 반응 지연 증거로 사용하지 않았다.**

이번에는 전체 7개 게임 완주, 모든 난이도, Safari·실제 모바일 키보드, 화면 읽기 프로그램, 확대 200/400%, 실기기 성능을 전수 재검사하지 않았다. 결과 화면 관련 항목은 코드 확인으로 구분했다. 기존 자동 테스트 통과 여부를 ‘사용자의 기대 충족’의 증거로 대신하지 않았다.

### 적용한 평가 기준

상태를 알 수 있는지, 사용자의 표현과 맞는지, 잘못 누른 행동을 취소할 수 있는지, 손실을 예방하는지를 기준으로 삼았다. 이는 일반적인 UX 평가 원칙이지 이 앱의 사용성이 인증됐다는 뜻은 아니다. [NN/g 사용성 원칙](https://www.nngroup.com/articles/ten-usability-heuristics/)

조작부의 모양·이름·역할이 실제 기능과 맞는지, 확인창이 키보드와 초점을 올바르게 다루는지도 확인했다. [W3C 버튼 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/button/), [W3C 모달 대화상자 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

작은 화면에서 콘텐츠와 기능이 사라지거나 양방향 스크롤을 강요받는지와, 시작 행동을 쉽게 발견하는지는 별개로 평가했다. 세로 스크롤이 있다는 사실만으로 접근성 위반이라고 판단하지 않는다. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

웹 인터페이스 가이드의 의미에 맞는 조작부·초점·손실 방지 항목도 대조했다. [Vercel Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)

`ksleep-design`을 적용하되, `status: canonical`을 확인한 [이 앱의 디자인 정본](../../DESIGN.md)의 독립 게임 예외를 유지했다. CareLoop 콘솔의 색·레이아웃을 이 앱에 그대로 적용하지 않는다. [게임 구현 계약](../ux-game-revision.md) 역시 `status: canonical`이며, 해당 문서의 과거 배포 기록을 이번 사용성 검증으로 간주하지 않았다. 본 보고서는 새 정본이 아니라 미승인 개선 제안이다.

## 3. 기대와 실제 동작 대조

‘높음’은 시작 방해·입력 실패·진행 손실·다른 화면으로의 오인을, ‘보통’은 이해와 조작의 추가 부담을 뜻한다. UX 개선 우선도이며 보안 사고 등급이 아니다.

| ID / 우선도 | 사용자가 기대할 수 있는 일 | 확인한 실제 동작 | 평가와 제안 |
|---|---|---|---|
| U01 / 높음 | 하단 ‘▶ 플레이’를 누르면 시작 | 이미 선택된 화면을 다시 선택할 뿐 본문 변화 없음. 네 화면 크기에서 재현. Sylvie의 혼동 보고도 있음 | 화면 이동은 ‘게임’ + 재생이 아닌 아이콘. 실제 시작은 ‘게임 시작’ 한 곳으로 명확히 구분 |
| U02 / 높음 | ‘그만두기’를 취소하고 ‘계속하기’를 누르면 하던 문제 유지 | 첫 이야기 질문 2/4에서 누르면 동일한 이야기를 처음부터 다시 읽게 됨 | 단순 취소가 진행 상태를 초기화하면 안 됨. 시간 제한 중 중단은 별도의 명시적 처리 필요 |
| U03 / 높음 | ‘결과 보기’를 누르면 결과 확인 | 첫 이야기 마지막 답 뒤 누르면 ‘반응속도’ 준비 화면. 결과 카드는 없음 | 중간 단계는 ‘다음 게임 · 반응속도’, 실제 최종 결과로 갈 때만 ‘전체 결과 보기’ |
| U04 / 높음 | 반응속도의 ‘화면 어디든 누르세요’대로 화면을 누르면 응답 | ‘지금!’ 제목 클릭은 응답하지 않음. 게임 판 안 클릭은 성공 처리 | 현재 입력 범위를 유지하고 ‘아래 게임 영역을 누르세요’로 수정. 실제 판 경계를 명확히 표시 |
| U05 / 높음 | 난이도를 살펴보더라도 기존 진행이 바로 사라지지 않음 | 이야기 완료 후 이어가기 상태에서 챌린저 선택 → 즉시 ‘게임 7개 시작’으로 변경. 확인창 없음 | 완료 기록이 있을 때만 변경 전 확인. 취소하면 기존 난이도와 기록 보존 |
| U06 / 높음 | 나가기 확인창에서 안전하게 취소하고 창 안에서 조작 | 첫 초점이 ‘네, 그만할게요’. Tab으로 창 밖 소리·그만두기로 이동. Escape로 닫히지 않음 | 안전한 행동에 첫 초점, 창 내부 초점 순환, Escape 취소, 닫힌 뒤 원래 초점 복원 |
| U07 / 보통 | 시작 전에 읽는 시간과 기억할 범위를 알 수 있음 | ‘준비됐어요’ 뒤 읽기 제한 시작. 준비 화면에 25초 미표시. ‘4가지 사실’이지만 앞뒤 서로 다른 질문을 각 4개씩 묻는 구조 | 준비 단계에 25초·한 번 읽기·앞뒤 다른 질문·첫 정답 비공개를 미리 안내. ‘퀴즈 앞뒤 각 4문제’로 정확히 표현 |
| U08 / 보통 | ‘다음 문제’ 버튼을 누를 때 다음으로 이동 | 색깔 단어 정답 뒤 아무것도 누르지 않아도 약 900ms 후 다음 문제. 오답은 직접 다음을 눌러야 함 | 읽고 확인하는 퀴즈는 수동 다음을 기본으로 통일. 신호 게임의 연속 시행은 별도 규칙으로 명시 |
| U09 / 보통·가설 | 큰 개별 게임 카드를 누르면 그 게임을 실행 | 패턴 게임 카드 제목 클릭 시 본문 변화 없음. 카드 안 ‘방법’만 펼쳐짐 | ‘코스 순서’라는 목록으로 표현하고 ‘방법 보기’만 조작부로 구분. 개별 실행 기대가 얼마나 생기는지는 참가자 확인 필요 |
| U10 / 보통·코드 확인 | 결과에서 내 기록 변화와 숫자의 의미를 이해 | 변화 비교를 설명하지만 저장·과거 기록 화면은 없음. 숫자 성공이 없으면 ‘최대 0자리’로 표시하는 코드 | ‘이번 코스 결과’로 범위 축소, 저장 안 됨을 위에 표시. ‘성공한 길이 없음’으로 사실만 설명 |

U05에는 이미 ‘난이도를 바꾸면 끝낸 N개 게임의 기록은 사라져요’라는 경고 문구가 있다. 문제는 **경고가 전혀 없는 것**이 아니라, 클릭과 방향키 선택만으로 되돌릴 수 없는 초기화가 일어난다는 점이다. 방향키 초기화 경로는 코드로 확인했고, 운영 재현은 클릭으로 했다.

U07의 준비 화면·읽기 시작은 운영 앱에서 확인했다. 앞뒤 질문 수와 분리는 코드 확인을 함께 사용했다. ‘몇 가지 사실만 기억하면 된다’는 해석을 유도하지 않는 문구가 필요하다.

추가 작은 마찰: 숫자 뒤집기에서 3자리 중 1자리만 입력하면 ‘답 제출’이 비활성화되지만 입력창 옆에 남은 자리 수가 없다. 운영 앱에서 재현했다. `1 / 3자리 입력 · 2자리를 더 입력하세요`처럼 활성화 조건을 알려주는 보완을 제안한다. 자동 제출로 바꾸지는 않는다.

## 4. 반응형 평가 — 배치가 맞는 것과 행동을 찾는 것은 다르다

아래는 첫 화면의 실제 버튼 경계 측정이다. 세로 좌표 단위는 CSS px이고, 실제 시작 버튼 전체가 하단 고정 메뉴 위에 있는지를 검사했다.

| 화면 크기 | 가로 넘침 | 시작 버튼 위–아래 | 하단 메뉴 시작 | 스크롤 없이 시작 버튼 전체 보임 |
|---|---|---|---|---|
| 390×844 | 없음 | 553–618 | 779 | 예 |
| 768×1024 | 없음 | 598–663 | 959 | 예 |
| 1440×900 | 없음 | 382–447 | 835 | 예 |
| 320×568 | 없음 | 592–657 | 503 | 아니요 |

**기본 반응형은 작동한다. 그러나 작은 화면의 행동 우선순위는 충분하지 않다.** 320×568에서는 실제 시작 버튼이 첫 화면 아래에 있고, 잘못된 시작 기대를 만드는 하단 플레이는 보인다. 제목도 ‘머리를 깨우 / 는’으로 나뉘어 장식과 제목이 좁은 폭을 나눠 쓰는 비용이 드러난다. 390px와 PC의 첫 화면 캡처도 직접 확인했다.

### 첫 화면 개선 제안

| 위치 | 제안 내용 | 설계 이유 |
|---|---|---|
| 상단 | 앱 이름·소리 조절, 짧은 소개 한 줄 | 시작 전에 읽어야 할 내용을 줄임 |
| 핵심 영역 | 난이도 → 한 줄 조건 요약 → ‘게임 시작’ | 선택과 실행을 가까이 둠 |
| 시작 보조 문구 | ‘7개 게임을 순서대로 진행해요. 먼저 방법을 안내해요.’ | 개별 게임 모음·즉시 시간 시작으로 오인하지 않게 함 |
| 진행 중 보조 문구 | 실제 보존 범위를 명시. ‘완료한 게임 다음부터 이어가요’ | 현재 진행 중인 답까지 보존된다고 약속하지 않음 |
| 그 아래 | ‘코스 순서’와 각 게임의 ‘방법 보기’ | 실행 버튼과 설명 목록을 분리 |
| 하단 이동 | ‘게임’ / ‘게임 안내’, 재생 아이콘 제외 | 화면 이동과 실행을 구분 |

라임 주 행동과 차콜 배경, 입체적인 게임 장면은 유지한다. 짧은 화면에서는 장식 구체를 축소하거나 숨기고 소개 여백을 줄인다. **글자와 터치 영역을 줄여 억지로 맞추지 않는다.** 기본 글자 크기 320×568에서도 실제 시작 버튼을 찾을 수 있게 재배치하고, 글자 확대 시에는 읽을 수 있는 크기와 세로 스크롤을 우선한다.

하단 플레이에 게임 시작 기능을 연결하는 임시 해결은 추천하지 않는다. 안내 화면에서 돌아오는 행동과 코스 실행·재시작이 섞이기 때문이다. 하단은 목적지, 본문의 주 버튼은 행동으로 역할을 고정한다.

## 5. 변경 시 지켜야 할 조건

### 진행 보존과 취소

U02는 버튼 이름만 바꿔서는 해결되지 않는다. 현재 나가기 창을 열 때 게임이 화면에서 제거되고, 계속하기는 새 게임 인스턴스를 만든다.

- 시간 제한이 없는 답 선택 단계: 창을 열고 취소해도 질문 번호·선택한 답·최초 답안이 유지되어야 한다. 본문을 다시 읽게 해서는 안 된다.
- 시간 제한 중인 자극·이야기 읽기 단계: 시간을 멈춘 뒤 정상 수행 기록으로 재개하면 과제 조건이 달라진다. 이를 일반 취소와 구분해야 한다.
- 시간 제한 단계에서 실제로 중단된 경우: ‘계속하기’라는 약속 대신 중단 사실과 필요한 재시작 단위를 명시한다. 특히 이야기 재노출이 발생하면 같은 이야기의 정상 코스 결과로 섞지 않고, 새 이야기로 시작하는 별도 흐름을 설계한다.
- 확인창만 열었다 닫는 동작과 실제 코스 종료, 앱이 백그라운드로 이동하는 중단을 구분한 상태 전이 검증이 필요하다. 이 보고서가 새로운 측정 프로토콜을 확정한 것은 아니다.

### 재미와 원형 과제 보존

- 반응속도·별똥별의 입체 효과는 응답 뒤 피드백에 사용한다. 신호가 나타나는 시점을 장식 애니메이션 때문에 늦추지 않는다.
- ‘화면 어디든’ 문제는 헤더까지 입력 범위를 무작정 확장하지 않고 현재 판 범위에 맞춰 안내를 고친다. 소리·나가기 클릭이 게임 답으로 섞이면 안 된다.
- 첫 이야기 퀴즈의 정답 비공개는 유지하되, 이유를 답 선택 전에 설명한다. 답을 골랐다는 접수 피드백은 즉시 준다. 이 경계를 단순한 정오답 편의 때문에 바꾸지 않는다.
- 뒤 이야기 퀴즈는 다른 질문을 유지한다. 앞뒤 정답률을 동일 문항의 기억 유지율로 해석하지 않는다.
- U08의 수동 다음 제안은 답을 제출한 뒤의 확인 화면에 해당한다. 숫자 제시 속도·색깔 단어 응답 기한·신호 게임의 대기 조건을 느슨하게 만드는 제안이 아니다. 진행 간격 변화는 이야기 지연 간격에 영향을 주므로 구현 계약에도 남겨야 한다.
- 게임 카드를 각각 실행할 수 있게 만드는 기능은 이번 추천에 포함하지 않는다. 이야기의 앞뒤 순서와 중간 활동이 달라지는 별도 모드 설계이기 때문이다.
- 기록 저장·로그인·진단·또래 백분위는 추가하지 않는다. 결과에서는 이번 게임에서 관찰한 사실과 해석의 한계를 구분한다.

## 6. 개선안을 ‘검증됨’으로 부르기 위한 통과 기준

다음은 **아직 실행하지 않은 개선 후 검증 계획**이다. 이번에 확인한 현재 동작과 혼동하지 않는다.

| 검증 | 개선 후 통과 기준 |
|---|---|
| 시작과 이동 | ‘게임’ 탭은 게임 선택 화면으로만 이동. ‘게임 시작’은 방법 안내로 이동. 새로고침 직후와 안내에서 돌아온 경우 모두 동일 |
| 취소 | 질문 2/4의 답 선택 전·후 각각 나가기 취소 → 같은 질문·선택 상태. 이야기 재노출·중복 채점 없음 |
| 시간 제한 중 중단 | 읽기·숫자 노출·신호 대기/노출 중 각각 확인. 중단된 기록이 정상 결과에 섞이지 않고, 화면 문구와 실제 재시작 단위 일치 |
| 다음 목적지 | 모든 게임의 마지막 행동 문구가 실제 도착 화면과 일치. 중간 게임에서 ‘결과 보기’ 거짓 약속 없음 |
| 응답 영역 | 문구가 가리킨 판의 중앙·가장자리 입력은 접수. 판 밖·소리·나가기는 게임 응답에 포함되지 않음 |
| 난이도 | 진행 없을 때 바로 선택 가능. 완료 기록이 있을 때 클릭·방향키로 변경해도 명시 확인 전 기록 유지. 취소 시 완전 복원 |
| 확인창 | Tab/Shift+Tab이 창 안에 머묾. Escape 취소. 초기 초점은 안전한 행동. 닫힌 뒤 의미 있는 위치로 초점 복귀 |
| 피드백 | 퀴즈 다음 이동을 사용자가 예측 가능. 자동 이동이 남는 과제는 사전 설명과 실제 시점이 일치. 빠른 연속 입력으로 이중 이동하지 않음 |
| 반응형 | 이번 4개 크기 + 가로 844×390, 데스크톱 1920px, 확대 200/400%, 실제 모바일 키보드에서 글자·입력·다음 행동이 가려지지 않음 |
| 결과 | 성공한 숫자 길이가 없을 때 능력 0으로 오인하는 문구 없음. 저장 안 됨이 첫 결과 영역에서 보임. 검사·진단·자동 변화 추적을 약속하지 않음 |

### 사람의 기대 검증

자동 클릭 검사만으로 ‘이해하기 쉬워졌다’고 결론내리지 않는다. 다음은 이 앱을 처음 보는 참가자 5명을 대상으로 한 **초기 소규모 테스트 제안**이다. 5명은 이번 작업의 운영상 제안이지 통계적 대표성을 보장하는 수가 아니다. 현재 참가자 모집이나 테스트는 하지 않았다.

1. ‘루키로 게임을 시작해 보세요.’ 버튼 이름을 먼저 알려주지 않고 첫 클릭, 주저한 위치, 도움 요청, 실제 안내 도달을 기록한다.
2. ‘안내를 보고 게임 화면으로 돌아와 보세요.’ 돌아가기와 시작을 구분하는지 확인한다.
3. ‘게임 도중 나가려다가 마음을 바꿨다고 해보세요.’ 취소 전에 무엇이 유지될 것으로 예상하는지 묻고 실제 결과와 비교한다.
4. ‘이 버튼을 누르면 어디로 갈 것 같나요?’ 마지막 문항의 다음 행동에서 예상 목적지와 도착 화면을 대조한다.
5. 반응속도 시작 전에 누를 곳을 짚게 하고, 결과 후에는 기록 저장 여부와 결과 의미를 본인 말로 설명하게 한다.

프로젝트 통과 목표: 5명 모두 진행 손실 없이 취소하고, 최소 4명이 도움 없이 첫 시도에 실제 시작 행동을 찾으며, 각 버튼의 예상 목적지와 도착지가 맞아야 한다. 한 명이라도 예기치 않은 기록 손실을 경험하면 재설계한다. 성공률은 참가자 수와 함께 보고하고 전체 사용자 비율로 일반화하지 않는다. 재테스트는 이미 화면을 외운 사람이 아닌 새 참가자로 시작 발견 가능성을 확인한다.
