# UI 루프 — 화면 품질을 게이트로 관리하는 개발 워크플로우

## 1. 왜 만드는가

### 1-1. 관찰된 사실

2026-09-02, 배포된 인지 컨디션 체크 앱(`https://ksleep-care-cognitive-check.vercel.app/`)을
실제 Chrome으로 렌더링해 관찰한 결과다.

| 항목 | 상태 | 근거 |
|---|---|---|
| 디자인 방향 문서 | 있음 | `DESIGN.md` |
| 색 토큰 정본 | 있음 | `src/tokens.css` |
| 대비 검증기 | 돌고 있음. **위반 0건 / 통과 11건** | `docs/design/token-report.md` |
| 화면 품질 | **나쁨** | 아래 §1-2 |

즉 **규칙이 없어서 못생긴 것이 아니다.** 규칙이 색 대비 하나만 검사하고,
나머지(정보구조·위계·밀도·중복·신뢰)는 아무도 보지 않기 때문이다.

### 1-2. Sylvie가 지적한 문제 4건 (2026-09-02)

1. 첫 화면(홈 탭)이 이 게임을 할지 말지 결정하게 해야 하는데 흥미를 전혀 못 일으킨다. 그리고 그 화면 자체가 불필요하게 느껴진다.
2. 각 화면 상단의 제목이 하단 탭 이름과 그대로 중복된다.
3. 모든 색이 청블루 한 계열이라 구분이 안 되고, 모든 것이 박스 안에 들어가 있어 전형적인 AI slop처럼 보인다. 공간 사용이 비효율적이라 계속 스크롤해야 한다 (예: 게임 7개를 세로로 길게 나열).
4. 각 게임 설명이 "무슨 게임인지"만 말하고, 이것이 국제적으로 공인된 인지기능검사를 커스터마이징한 것이라는 신뢰 근거를 주지 않는다.

### 1-3. 기계로 측정된 증거

`browse ux-audit` 실측값:

- H1 `인지 컨디션 체크` = 22px, H2 `3분 집중 측정` = 19px → **크기 비 1.16**. 제목과 소제목이 사실상 같은 크기다. Sylvie 지적 3번("위계 없음")의 정량 근거.
- `youAreHere` 항목 텍스트가 `🏠홈` → 탐색 아이콘이 이모지다.
- `index.html`의 `theme-color`가 아직 `#FAF8F2`(베이지). 화면은 어두운 밤하늘로 바뀌었으나 이 값만 옛것이다 → **문서·토큰은 갱신됐는데 실제 화면을 아무도 확인하지 않았다는 증거.**

### 1-4. 도구 상태 실측 (2026-09-02)

| 도구 | 조치 전 | 조치 후 |
|---|---|---|
| gstack `browse` CLI | PATH에 없어 디자인 스킬 3개(`design-review`, `design-shotgun`, `qa`)가 화면을 못 봄 | `~/.local/bin/browse` 심볼릭 링크 생성. `browse status` = healthy, `browse ux-audit` 정상 동작 확인 |
| Claude Design MCP (`/design`) | HTTP 403 로그인 거부 | **미해결.** Sylvie가 `/design-login`을 직접 실행해야 함 (OAuth 브라우저 로그인) |
| Playwright + 시스템 Chrome | 미사용 | 스크린샷 촬영 검증 완료 |
| 색 대비 검증기 | 정상 | 정상 (UI 루프 게이트 3에 편입) |

## 2. 목표와 비목표

### 목표

- 화면 품질을 사람의 감이 아니라 **통과·실패가 갈리는 게이트**로 관리한다.
- 기계가 잡을 수 있는 것은 전부 기계가 잡는다. 사람은 취향 판단만 한다.
- Sylvie는 마지막에 **before/after 사진 2장과 3줄 요약**만 본다.
- 이번에 지적된 4개 문제가 **다시 발생하면 자동으로 걸린다.**

### 비목표

- 디자인 취향을 AI가 최종 결정하는 것. 취향은 항상 Sylvie가 고른다.
- 새 디자인 시스템 제작. `DESIGN.md`와 `ksleep-design`이 이미 정본이다.
- gstack 스킬 대체. 그것들은 살려서 이 워크플로우 안에서 호출한다.
- 의료 진단·정상 판정·연령 백분위. 이 앱의 기존 경계를 그대로 유지한다.

## 3. 게이트 5개

```
G1 화면 계약  →  G2 시안 비교  →  G3 코드 검사  →  G4 화면 검사  →  G5 승인
  (사람 5분)      (Sylvie 선택)     (자동)          (자동+AI)       (Sylvie)
   코딩 전         코딩 전          코딩 중          코딩 후          배포 전
```

### G1 — 화면 계약 (코딩 전, 사람)

새 화면을 만들거나 기존 화면을 크게 고치기 전에 화면당 5줄을 적는다.

| 칸 | 내용 | 예 |
|---|---|---|
| 목적 | 이 화면이 사용자에게 시키려는 단 하나 | "오늘 측정을 시작하게 만든다" |
| 주 행동 | 화면에서 가장 큰 버튼 하나 | "3분 측정 시작" |
| 스크롤 예산 | 뷰포트 몇 배까지 허용 | 1.2 |
| 강조색 | 2개까지 | violet, lime |
| 금지 | 이 화면에서 특별히 하면 안 되는 것 | "움직이는 배경 금지 (PVT 오염)" |

저장 위치: 프로젝트의 `docs/design/screens.md`.

**실패 조건:** 목적 칸을 한 문장으로 못 적으면 그 화면은 만들지 않는다.
Sylvie 지적 1번("이 화면 자체가 불필요하게 느껴짐")을 원천 차단하는 장치다.

### G2 — 시안 비교 (코딩 전, Sylvie 선택)

바로 React를 고치지 않는다. 정적 HTML 시안 **2~3개**를 만들고 스크린샷을 나란히 놓는다.

- 시안은 실제 토큰(`src/tokens.css`)과 실제 문구를 쓴다. 로렘입숨 금지.
- 각 시안은 **접근 방식이 명확히 달라야** 한다. 색만 바꾼 대조군은 만들지 않는다.
- Sylvie는 번호만 고른다. 고른 뒤에만 React 구현이 시작된다.

**여기가 "촌스러움"을 막는 유일한 지점이다.** 나머지 게이트는 전부 이미 정해진 방향의 실행 품질만 본다.

### G3 — 코드 검사 (코딩 중, 자동)

명령: `npm run ui:check`

소스코드만 읽고 판정한다. 브라우저를 띄우지 않으므로 빠르다. 규칙은 §4 표의 자동(코드) 항목.

### G4 — 화면 검사 (코딩 후, 자동 + AI 판독)

명령: `npm run ui:shots`

1. 시스템 Chrome을 띄워 화면마다 스크린샷을 찍는다 (모바일 390×844, 데스크톱 1440×900).
2. 각 화면의 `scrollHeight ÷ 뷰포트 높이`, 제목 크기 비, 사용된 색상(hue) 종류, 최소 터치 영역을 측정한다.
3. 임계값을 넘으면 실패로 표시한다.
4. AI가 저장된 스크린샷을 **직접 보고** §4의 사람 판단 항목을 채점한다.
5. 실패 항목을 고치고 다시 1번부터. 통과할 때까지 반복한다.

저장 위치: `docs/design/shots/<화면>-<뷰포트>.png`, 리포트는 `docs/design/ui-report.md`.

### G5 — 승인 (배포 전, Sylvie)

제출물은 3개뿐이다.

1. before 스크린샷
2. after 스크린샷
3. 바뀐 점 3줄

Sylvie는 OK 또는 NO만 답한다. NO면 G2로 되돌아간다.

이번에 지적된 문제에서 직접 도출한 규칙이다. 규칙마다 "어느 지적에서 나왔는지"를 남긴다.

| 경로 | 내용 |
|---|---|
| `~/.claude/skills/ui-loop/SKILL.md` | 게이트 순서, 언제 어느 기존 스킬을 부르는지, 판독 체크리스트 |

| `~/.claude/skills/ui-loop/rules.default.json` | 임계값 기본값 |
| 프로젝트: `ui-loop.config.json` | 화면 목록, URL, 뷰포트, 프로젝트별 임계값 |

스킬은 **전역 1개**, 설정은 **프로젝트마다 1개**다. 스킬을 프로젝트에 복사하지 않는다.

## 6. 기존 스킬을 언제 부르는가

새로 만들지 않고 이미 있는 것을 순서에 꽂는다.

| 상황 | 부를 것 | 어느 게이트 |
|---|---|---|
| 새 프로젝트에 디자인 시스템이 없음 | `design-consultation` | G1 앞 |
| K-Sleep 제품의 색·타이포·밀도 규칙 확인 | `ksleep-design` | G1 |
| 시안 여러 개 만들어 비교 | `design-shotgun` (browse 복구로 사용 가능해짐) 또는 `/design` 캔버스 (로그인 필요) | G2 |
| 랜딩·마케팅 페이지의 안티슬롭 감각 | `design-taste-frontend` | G2 |
| 이미지를 먼저 만들고 코드로 옮김 | `image-to-code` | G2 |
| 계획 단계에서 디자인 관점 검토 | `plan-design-review` | G1~G2 |
| 접근성·웹 표준 코드 검토 | `web-design-guidelines` | G3 |
| 라이브 화면 시각 QA와 자동 수정 | `design-review` (browse 복구로 사용 가능해짐) | G4 |
| 동작 버그까지 훑기 | `qa` | G4 뒤 |

`/design` 캔버스는 G2에서 가장 쓸모가 크지만 현재 로그인이 막혀 있다. 복구 전에는 `design-shotgun`으로 대체한다.

## 7. 검증 방법

이 워크플로우가 실제로 작동한다는 증거는 다음으로 삼는다.

1. `npm run ui:check`와 `npm run ui:shots`를 **고치기 전** 코드에 돌린다.
2. 리포트가 §1-2의 지적 4건과 §1-3의 실측 3건을 **자동으로 잡아내야 한다.**
   - 잡히지 않는 항목이 있으면 그 규칙은 잘못 설계된 것이므로 고친다.
3. 그다음 화면을 고치고 다시 돌려 전부 통과시킨다.
4. before/after 스크린샷을 남긴다.

즉 **이번 문제들을 재현해서 잡는 것**이 합격 기준이다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 규칙이 너무 빡빡해 개발이 막힘 | 규칙마다 `warn`/`fail` 등급을 둔다. 처음엔 6·10·11을 `warn`으로 시작 |
| 임계값이 근거 없이 정해짐 | 임계값은 전부 `rules.default.json`에 두고, 바꾼 이유를 커밋 메시지에 남긴다 |
| 스크린샷 촬영이 느림 | G3(코드)는 빠르므로 자주 돌리고, G4(화면)는 커밋 전·배포 전에만 돌린다 |
| gstack `browse`가 업데이트로 다시 깨짐 | 심볼릭 링크 대상이 사라지면 Playwright + 시스템 Chrome으로 대체하는 경로를 스킬에 함께 적어둔다 |
| PVT 측정 화면에 애니메이션 규칙이 잘못 적용됨 | `screens.md`의 금지 칸에 명시. G4에서 PVT 화면은 움직임 검사를 별도 적용 |
| 이 앱의 의료 경계 침범 | 워크플로우는 화면 표현만 다룬다. 진단·판정 문구 생성은 범위 밖 |

## 9. 이번 범위 밖

- 게임 로직·측정 계약 변경 (3분 PVT 표준 등)
- 백엔드·데이터 저장
- 다른 프로젝트로의 확산 (스킬은 전역이지만, 설정 적용은 프로젝트별로 그때그때)
